# レビューコメント規約

[English](REVIEW_COMMENTS.md)

対応を求めるレビューコメントには、次のプレフィックスを付けます。

```text
ACTION(Viewpoint): 簡潔な説明
```

## 対応要否

- `MUST`：マージ前に解決が必要な、根拠のある問題
- `SHOULD`：通常は解決すべき具体的な品質・保守上のリスク。チームが明示的に判断すれば
  延期できる
- `BETTER`：具体的な利点がある任意の代替案。現在の実装も受け入れ可能
- `NITS`：軽微でマージを妨げない修正。限定的に使用し、自動整形の結果には使わない

分類はモデルとの一致ではなく、確認した契約と影響で決めます。必須のrepository規約への違反や
起動に失敗するsetup説明は`MUST`、明示的に延期できる設計上の助言は`SHOULD`です。
変更で未使用になった小さなprivate helperを、動作への影響なく削除する修正は
`NITS(Simplicity)`とし、任意の再設計提案とは区別します。

## レビュー観点

- `Design`：アーキテクチャ、責務、依存関係、境界
- `Simplicity`：理解や保守に具体的なコストを生む複雑さ
- `Naming`：動作や重要な制約を正しく表さない識別子
- `Style`：自動化されていない、確立済みのプロジェクト規約
- `Functionality`：正しさ、interface、security、reliability、performance、privacy、運用動作
- `Test`：特定のregressionを検出するために不足または無効な検証
- `Document`：利用者、API、setup、migration、comment、運用に関する不正確・不十分な説明

## コメントの記載ルール

作成者を評価せず、コードで観察できる動作を説明します。根拠を発生条件と影響へ結び付け、
指摘が必要な理由と、受け入れ可能な結果または適切な修正方向を示します。敬意のある
中立的な言葉を使い、事実と推測を区別します。

contextが不足している場合は、不確実な内容をfindingとして断定せず質問します。任意の
コメントを必須に見せず、必須のコメントを曖昧にしません。個人の好みよりプロジェクト
規約とチームの一貫性を優先し、1コメントにつき1つの根本原因を扱います。対応すべき
問題がない場合、価値の低いコメントを作りません。

質問や要約の事実上の前提も検証します。未確定の意図についての重要な質問は指摘と分け、
断りを付けても架空の事実を許しません。変更していない挙動を対象外と説明する正確で
対応不要の注記は指摘ではありませんが、修正要求や無関係な欠陥の羅列はしません。

例：

```text
MUST(Functionality): 次の結果を取得する前にページ番号を進める

APIが上限件数を返すと、`page`が更新されないため同じページを再度取得します。その結果、
`maxPages`まで結果が重複し、リクエスト数も増えます。各iterationで新しい結果を取得
できるよう、次のリクエスト前にページ番号を進めてください。
```
