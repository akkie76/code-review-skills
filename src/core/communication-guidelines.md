# Review Comment Communication Guidelines

Use review comments to make a shared engineering decision easier, not to prove
the reviewer right. Technical accuracy and respectful delivery are both part
of an effective comment.

Before sending a comment, confirm that it:

- Makes the expected response clear through its action level.
- Describes the observed code behavior before judging it.
- Gives a reason tied to user, system, team, or maintenance impact.
- States the expected outcome while leaving room for a different valid fix.
- Distinguishes a verified problem from a question about missing context.
- Uses wording that would remain appropriate regardless of the author's role
  or experience.

Avoid comments that only say to change something, label code as bad, assume the
author's intent, or elevate individual taste into a team rule. If a suggestion
is optional, explicitly preserve the author's choice. If a correction is
required, be courteous without making the requirement ambiguous.

When a comment thread cannot resolve a missing requirement or design decision,
surface that decision as an open question. The goal is a clear next action, not
an indefinitely longer thread.
